# ระบบเว็บไซต์การแข่งขันแบดมินตัน กีฬาภายใน ทอท. 2569

เว็บไซต์แสดงตารางแข่ง ผลการแข่งขัน สายการแข่งขัน และคะแนนสี แบบเรียลไทม์
พร้อมระบบผู้ดูแลสำหรับกรอกข้อมูลจริงเมื่อถึงเวลาแข่ง

โครงสร้างการแข่งขันทั้งหมด **มาจากไฟล์ `AOT_Badminton_2569_Production_Data.xlsx`**
และถูกตรวจความครบถ้วนซ้ำทุกครั้งที่นำเข้า

| รายการ | จำนวน |
|---|---|
| สี | 4 (ม่วง เขียว แดง น้ำเงิน) |
| ระดับมือ | 4 (มือใหม่ · มือ D · มือ C · มือทั่วไป) |
| คู่แข่งขัน | 92 |
| นักกีฬา | 184 |

## สถานะปัจจุบัน

ระบบ **ทำงานได้ครบแล้ว** และรอเพียงข้อมูลจริง 4 อย่างที่ยังไม่มีในวันที่สร้าง:

| ข้อมูลที่ยังรอ | กรอกที่ไหน | ก่อนกรอกเว็บแสดงอะไร |
|---|---|---|
| วันแข่งจริง + สถานที่ | `/admin/settings` | "วันที่ 1-3" และ "สถานที่ยังไม่ยืนยัน" |
| ชื่อนักกีฬา 184 คน | `/admin/participants` | รหัสชั่วคราว เช่น `ม่วง_LEVEL1_MD_1-1` (ตัวเอียงสีจาง) |
| ประเภท MD/WD/XD ของมือ C และมือทั่วไป (28 คู่) | `/admin/participants` | ป้าย "รอเลือกประเภท" |
| ผลจับสลาก 80 ช่อง + ซองรายชื่อมือทั่วไป | `/admin/draw`, `/admin/lineups` | "รอจับสลาก · ชายคู่ สาย 1" ฯลฯ |

ระบบ **ไม่เดาข้อมูลที่ยังไม่มี** — ทุกช่องที่ยังไม่รู้จะแสดงที่มาแทน เช่น
"ผู้ชนะแมตช์ #12", "อันดับ 1 กลุ่ม A", "รอส่งซอง · คู่ที่ 2"
เมื่อกรอกข้อมูลจริงเข้าไป สายทั้งหมดจะคลี่ต่อเองอัตโนมัติ

## เริ่มใช้งาน

### 1. เตรียมฐานข้อมูล

ต้องมี PostgreSQL (แนะนำ Neon / Supabase / Railway / RDS)

```bash
cp .env.example .env
```

แก้ `.env`:

- `DATABASE_URL` — connection string ของ Postgres
- `AUTH_SECRET` — สุ่มใหม่ทุกครั้งก่อนขึ้น production:
  ```bash
  node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
  ```
- `SEED_SUPERADMIN_USERNAME` / `SEED_SUPERADMIN_PASSWORD` — บัญชีหัวหน้าผู้ดูแลคนแรก
  (เปลี่ยนรหัสผ่านได้เองที่เมนู "เปลี่ยนรหัสผ่าน" ในระบบผู้ดูแล — แนะนำให้เปลี่ยนหลังเข้าครั้งแรก)

### 2. ติดตั้งและนำเข้าข้อมูล

```bash
npm install
npm run db:push
npm run db:seed
npm run dev
```

เปิด http://localhost:3000

### 3. ขึ้น production

```bash
npm run build
npm start
```

บน Vercel/Railway ตั้ง environment variables ให้ครบตาม `.env.example`
คำสั่ง build ของโปรเจกต์รัน `prisma generate` ให้เองแล้ว

### หัวใจของระบบ: `src/lib/engine`

ตารางแมตช์ไม่ได้เก็บว่า "คู่ไหนแข่งกับคู่ไหน" แต่เก็บ **ที่มาของแต่ละฝั่ง** ตามชุดข้อมูลต้นทาง:

| รูปแบบ | ความหมาย | รู้ผลเมื่อไร |
|---|---|---|
| `SEED:L1:MD:01` | สายที่ 1 ชายคู่ มือใหม่ | หลังจับสลาก |
| `GROUP:L2:A:SLOT1` | คู่ที่ 1 ของกลุ่ม A มือ D | หลังจับสลาก |
| `GROUP_RANK:L2:A:1` | อันดับ 1 ของกลุ่ม A | หลังจบรอบแบ่งกลุ่ม |
| `WINNER:MD-SF1` / `LOSER:MD-SF1` | ผู้ชนะ/ผู้แพ้ของแมตช์นั้น | หลังแมตช์นั้นจบ |
| `LINEUP:L4:T01:PUR:ORDER1` | คู่ที่ 1 ในซองของสีม่วง คู่สีที่ 1 | หลังส่งซอง |

เอนจินคลี่ทั้งหมดนี้ให้เองในการคำนวณรอบเดียว แล้วคืนทั้ง
คู่ที่แข่งจริง อันดับกลุ่ม อันดับสีของมือทั่วไป ผลคู่สี และคะแนนสีพร้อมที่มา

เนื่องจากเป็นฟังก์ชันบริสุทธิ์ จึงทดสอบได้โดยไม่ต้องมีฐานข้อมูล:

```bash
npm run simulate          # จำลองด้วยเมล็ดสุ่มค่าเริ่มต้น
npm run simulate -- 42    # กำหนดเมล็ดสุ่มเอง (ผลซ้ำได้)
```

## กติกาที่ระบบบังคับให้เอง

- **สกอร์** Best of 3 · ชนะที่ 21 ต้องห่าง 2 แต้ม · เพดาน 30 (จบได้ที่ 30-29) ·
  ต้องมีฝ่ายชนะครบ 2 เกม · เกมที่ 3 มีได้เมื่อเสมอ 1-1
- **Walkover** บันทึกเป็น 21-0, 21-0 ให้ฝั่งที่มาแข่ง และต้องระบุเหตุผล
- **มือทั่วไป** 1 คู่สี = 3 แมตช์ · ชนะ 2 ใน 3 · **ต้องแข่งครบทั้ง 3 แมตช์** ระบบจึงปิดคู่สี
- **ซองรายชื่อ** คู่ที่ 1 ต้องมีระดับมือไม่ต่ำกว่าคู่ที่ 2 และ 3 · ห้ามส่งคู่ซ้ำ ·
  แก้ไม่ได้เมื่อคู่สีเริ่มแข่งแล้ว
- **มือ D ไม่มีประเภทชายคู่**
- **ประเภทคู่ต้องตรงกับเพศ** MD = ชาย 2 · WD = หญิง 2 · XD = ชาย 1 หญิง 1
- **ระดับมือต้องอยู่ในเกณฑ์ของระดับที่ลงแข่ง** (เช่น มือใหม่รับเฉพาะ NEW)
- **รหัสพนักงานห้ามซ้ำ** ข้ามทุกสีและทุกระดับ
- **สายล่าง L2/L3** ชนะเลิศได้ 0.5 คะแนน · ชิงอันดับ 3 คงแมตช์ไว้แต่ **0 คะแนนและไม่มีอันดับ**
- **คะแนนสีรวม** ต้องเท่ากับ 37 พอดี (ตรวจทั้งตอน seed และตอน simulate)
- **เกณฑ์เสมอคะแนนสีรวม** เหรียญทอง > เหรียญเงิน > เหรียญทองแดง

### เกณฑ์จัดอันดับเมื่อคะแนนเท่ากัน

ใช้ทั้งรอบแบ่งกลุ่มและอันดับสีของมือทั่วไป ตามลำดับ:

1. ชนะมากกว่า
2. ผลการเจอกันเอง
3. ผลต่างเกม
4. ผลต่างแต้ม
5. คำชี้ขาดของคณะกรรมการ (บันทึกในตาราง `tiebreak_decision`)

ถ้ายังแยกไม่ออก ระบบจะ **ไม่เดา** แต่ขึ้นคำเตือนในหน้าผู้ดูแลว่าต้องให้กรรมการตัดสิน
(ตรงกับรายการ Blocking "ยืนยันเกณฑ์เสมอขั้นสุดท้ายมือทั่วไป" ที่ยังรอมติ)

## สิทธิ์ผู้ใช้

| บทบาท | ทำอะไรได้ |
|---|---|
| ผู้กรอกผล (SCORER) | กรอกสกอร์ เปลี่ยนสถานะแมตช์ บันทึก Walkover |
| ผู้ดูแลระบบ (ADMIN) | ทุกอย่างของ SCORER + รายชื่อนักกีฬา จับสลาก ซอง ตั้งค่า ล้างผลรายแมตช์ ดูประวัติ |
| หัวหน้าผู้ดูแล (SUPERADMIN) | ทุกอย่างของ ADMIN + จัดการบัญชี เปิด/ปิดโหมดระบบ ล้างผลทั้งหมด |

หน้าสาธารณะ **อ่านอย่างเดียว ไม่ต้องเข้าสู่ระบบ** และไม่ส่งรหัสพนักงานออกไปกับข้อมูล

ทุกการแก้ไขเขียน audit log ในทรานแซกชันเดียวกับการแก้ข้อมูล ดูได้ที่ `/admin/audit`

## ก่อน Go-live

ดู Checklist ทั้งหมดที่ `/admin` (นำมาจากชีต `Production_Check` ของ Excel)
รายการที่ทำเครื่องหมาย "ต้องผ่าน" ต้องเป็น "พร้อม" ให้ครบก่อนเปิดใช้งานจริง

ประเด็นที่ระบบบังคับให้ได้เอง:

- `simulation_enabled` และ `public_admin_test_mode` ต้องเป็น **ปิด** —
  ถ้าเปิดค้างไว้จะมีแถบเตือนสีแดงทุกหน้าของผู้ดูแล
- ซ้อมระบบ: `/admin/settings` → เปิดโหมดจำลอง → กด **จำลองผลครบ 158 แมตช์**
  ระบบจะจับสลากและส่งซองให้อัตโนมัติเฉพาะช่องที่ยังว่าง แล้วสุ่มสกอร์ที่ถูกกติกาจนจบทุกแมตช์
- ล้างผลหลังซ้อมระบบ: หน้าเดียวกัน เลือกขอบเขต (เฉพาะผล หรือ ผล+จับสลาก+ซอง)
  ต้องพิมพ์ข้อความยืนยัน · หรือใช้ `npm run db:reset-results`
- HTTPS, security headers และ session cookie แบบ `httpOnly` + `Secure` ตั้งไว้แล้ว
  ที่เหลือให้ตั้ง rate limit และ monitoring ที่ชั้น hosting

- **`pair_uid` และ `participant_uid` เป็นรหัสถาวร** ห้ามใช้ชื่อคนเป็น primary key
- หน้าสาธารณะดึงข้อมูลทั้งชุดจาก `GET /api/public/snapshot` แล้วรีเฟรชตาม
  `public_refresh_ms` (ค่าเริ่มต้น 3 วินาที) หยุดดึงอัตโนมัติเมื่อผู้ใช้สลับแท็บออก
  และยังแสดงข้อมูลล่าสุดพร้อมบอกเวลาถ้าเน็ตหลุด
- ข้อมูลทั้งชุดเล็ก (158 แมตช์ / 92 คู่) จึงคำนวณสดทุกครั้งได้ ไม่มีสถานะซ้ำซ้อนให้ไม่ตรงกัน

### รันฐานข้อมูลในเครื่องด้วย Prisma Postgres

ถ้ายังไม่มี Postgres ในเครื่อง:

```bash
npx prisma dev -n live -P 55433
```

แล้วใช้ URL แบบ TCP ใน `.env`:

```
DATABASE_URL="postgres://postgres:postgres@localhost:55433/aot_badminton?sslmode=disable&pgbouncer=true&connection_limit=5"
```

ต้องมี `pgbouncer=true` และ `connection_limit=5` — ถ้าไม่ใส่ พูลเลอร์ของ `prisma dev`
จะค้างเมื่อมีคำสั่งพร้อมกันหลายรายการ ทั้งสองพารามิเตอร์นี้ใช้เฉพาะตอนพัฒนา
บน Postgres จริงไม่ต้องใส่
